# DHD Nexus Content Layer

This directory is the authoritative **Lesson Specification** layer for
DHD Nexus. It is a manifest/registry — plain, human-reviewable YAML —
that records learning intent, curriculum placement, misconceptions, and
artifact references for each lesson, independently of the React
implementation.

## What belongs here

- **`lessons/*.yaml`** — one Lesson Specification per lesson. Each file
  records: identity (`id`, `title`, `domain`, `topic`), purpose
  (`description`, `objectives`), curriculum relationships
  (`prerequisites`, `bridges`, `curriculumMaps`), pedagogy
  (`instruction`, `misconceptions`, `difficulty`), and a registry of the
  artifacts that realize the lesson (`artifacts`).
- **`misconceptions/*.yaml`** — one file per named misconception, each
  with a `statement` (the misconception itself) and a `correction`.
  Referenced by ID from any lesson's `misconceptions` list.
- **`curriculum/concepts.yaml`** — a flat registry of known concept IDs.
  This is what a lesson's `prerequisites` and `bridges` are checked
  against. It is intentionally a list, not a graph database.

## What does NOT belong here

- **No UI markup, JSX, or component code.** A lesson's artifacts array
  points at where the implementation lives (an app route, a file path)
  — the implementation itself is never embedded in the spec.
- **No raw lesson narrative or long-form written content.** A
  `description` is one or two sentences of *purpose*, not the lesson
  text itself. Long-form written content is its own artifact
  (`type: written`), referenced by path.
- **No student UI/progress state.** This layer describes what a lesson
  *is*, not what any individual student has done with it.
- **No derived data.** Anything computable from the fields above (a
  prerequisite graph, navigation relationships, artifact-availability
  summaries) is generated by tooling later — it is never hand-authored
  here.

## The Lesson Specification schema

The schema is frozen and lives in `content/schema/lessonSpec.types.ts`
and `content/schema/artifact.types.ts`. Required fields are non-optional
TypeScript properties; recommended and optional fields are marked
optional. There is no open-ended `[key: string]: unknown` escape hatch
— a field that isn't named in those two files isn't part of the schema,
by design. If a lesson genuinely needs a new field, add it to the
schema deliberately rather than inventing it in a YAML file.

### The 3+7 interaction model

Every Lesson Specification's `instruction` block requires three
pedagogical anchors:

```yaml
instruction:
  predict: "..."   # required
  explore: "..."   # required
  reflect: "..."   # required
  observe: "..."   # optional
  model: "..."     # optional
  # activate / apply / test / retrieve / explain are also optional
```

The remaining seven (`activate`, `observe`, `model`, `apply`, `test`,
`retrieve`, `explain`) are typed but never required — use them only
where they genuinely add pedagogical value for that specific lesson.

## Artifact references

An artifact reference never embeds the artifact itself:

```yaml
artifacts:
  - id: web-lab-acceleration
    type: web-lab          # web-lab | manim | marimo | video |
                            # worked-example | exam-question |
                            # retrieval-item | written
    status: implemented    # implemented | in-progress | planned
    location: /mechanics/kinematics/acceleration
    label: Acceleration Web Lab
```

`location` is an app route for a `web-lab`, or a relative file path for
everything else. It's optional because a `planned` artifact may not
have a location yet.

## Curriculum mappings

Deliberately flat — no nested hierarchy:

```yaml
curriculumMaps:
  ccmas: PHY101
  traditional: PHYS-101-KIN
```

## Relationship to the React implementation

Nothing in `content/` currently wires into `src/router/AppRouter.tsx`
or `src/components/academy/AcademyNavigation.ts`. The content layer and
the existing Kinematics/Dynamics implementation coexist without either
depending on the other. A lesson's `web-lab` artifact `location` is
simply the existing route — the spec *describes* what's already built;
it does not generate or control it.

## Running validation

```bash
npm run validate:content
```

This runs `scripts/validate-content.mjs`, which checks:

- **Structural** — malformed YAML, missing required fields, invalid
  field types, invalid artifact `type`/`status` values.
- **Identity** — duplicate lesson IDs, duplicate concept IDs, duplicate
  misconception IDs.
- **Relationship** — `prerequisites`/`bridges` resolve against
  `curriculum/concepts.yaml`; `misconceptions` resolve against files in
  `misconceptions/`; `assessmentRelationships` resolve against the
  lesson's own `artifacts`.
- **Curriculum** — `curriculumMaps` is a flat string-to-string object.

The script exits non-zero on any failure and prints every error found
(it does not stop at the first one). It can also be pointed at a
different content root for testing: `node scripts/validate-content.mjs
path/to/fixture`.
